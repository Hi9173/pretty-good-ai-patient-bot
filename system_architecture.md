# System Architecture

The system is a local-first live-call test harness for Pretty Good AI's voice bot. A single command, `python3 -m pgai_patient_bot.cli run-live-scenarios <scenario-or-range> --live`, starts the local public server, starts ngrok, verifies `/twiml` and `/media`, places the Twilio call, and streams Pretty Good AI's audio through a Twilio `<Connect><Stream>` WebSocket. The bridge forwards Twilio PCMU audio frames to OpenAI Realtime, where a scripted patient persona responds by voice; Realtime audio deltas are sent back to Twilio so the Pretty Good AI bot hears the simulated patient. After the call completes, the same workflow exports `recording.mp3`, writes `transcript.txt` and `analysis.md`, and records supporting files such as `audio_manifest.json` and `stream_status.jsonl` in numbered scenario folders like `calls/03_refill_missing_triage/`.

The main design choice was to keep normal development offline and deterministic while making live calls explicit and auditable. The media contract, fake WebSocket, fake Realtime connection, scenario fixtures, MP3 export, and analysis artifact shape are all testable without Twilio, OpenAI, ngrok, or paid API calls; live behavior is guarded behind `--live` commands and environment configuration. The public server combines `/twiml` and `/media` on one port to match ngrok's static-domain workflow, uses Twilio Stream `statusCallback` events to distinguish normal stream stops from WebSocket errors, and disables server keepalive pings so Twilio's long-running media stream is not closed by the local WebSocket server. The 10 numbered scenarios are structured data rather than hardcoded call logic, which lets the same bridge exercise scheduling, refills, emergency triage, language access, recording consent, account changes, and privacy/authorization edge cases.
